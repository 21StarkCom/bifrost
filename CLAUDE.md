# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Skill behavior comes from stark-skills. Keep runtime-specific changes upstream and regenerate both plugin formats. A shared-asset change re-vendors into EVERY bundle, so every bundle must bump. `check-bumps` enforces that: it digests the shared `vendor/stark-skills/` snapshot per bundle and fails naming each one, and `docs/scripts/publish.sh` patch-bumps them for you. Same rule, same gate, for a per-bundle Codex overlay under `vendor/runtime-overrides/codex/`.

`bifrost` (branded **Bifröst**; GitHub slug `21StarkCom/bifrost`) is the **canonical, multi-runtime marketplace** for stark bundles. The engine renders each bundle into per-runtime trees (`dist/claude/`, `dist/codex/`, `dist/gemini/`) plus a signed `index.json` / `bundles/*.json` registry. The repo doubles as a native **Claude Code marketplace** — `.claude-plugin/marketplace.json` at the repo root IS the manifest CC reads when you `/plugin marketplace add 21StarkCom/bifrost`.

**Source of truth = stark-skills.** The catalog's `skills/` + `commands/` are **generated** from a stark-skills checkout by `stark sync` (driven by each `bundle.yaml`'s `skills:`/`commands:` membership manifest); do NOT hand-edit them. What IS curated in this repo: each `bundle.yaml` (metadata + membership), and `mcp/` artifacts (stark-skills defines no MCP servers). See "Generation pipeline" below.

**Plugins are self-contained.** `stark build` vendors the stark-skills immutable assets (`tools/`, `prompts/`, `standards/`, `scripts/`, `config.json`, `forge_heuristics.json`) — from the committed `vendor/stark-skills/` snapshot — into every `dist/claude/<bundle>/`, and emits a per-bundle `.claude-plugin/plugin.json`. So `/plugin install <bundle>` works with **no install.sh** on the target machine. Skills resolve paths via `${CLAUDE_PLUGIN_ROOT}`. Runtime prereq: **Node ≥ 24** (plain `node` with native TypeScript and SQLite; `stark doctor` enforces this floor).

**Codex installs vendor the same assets (`codex@3`).** `stark install --runtime codex` writes `.agents/skills/<name>/SKILL.md`, native UI/invocation policy at `agents/openai.yaml`, that skill's `{references,scripts,assets}/`, and the bundle assets root at **`.agents/stark/<bundle>/`** (`tools/`, `standards/`, `prompts/`, `scripts/`, `data/persona/`, `config.json`). The root is **per bundle, never shared** — e.g. `stark-gh` (now retired) shipped its own `config.json` that would clobber the shared snapshot's in a flat namespace. `codex@3` drops unsupported per-skill `model` metadata and maps `disable-model-invocation` to `policy.allow_implicit_invocation`; command emulations are always explicit-only. Because the tree differs from a Claude plugin's, the target retargets reference shapes in every rendered body: `${CLAUDE_PLUGIN_ROOT…}` → `${STARK_PLUGIN_ROOT:-$HOME/.agents/stark/<bundle>}` (the `$HOME` fallback assumes a global install; export `STARK_PLUGIN_ROOT` for a project-local one), `${CLAUDE_PLUGIN_ROOT}/skills/<name>/…` → `${STARK_PLUGIN_ROOT:-…}/../../skills/…`, and any leading `../` run before `{tools,standards,prompts,scripts}/` → `../../stark/<bundle>/…`. Current Codex skill preambles export `STARK_ASSET_ROOT` so tool-internal asset resolution stays inside the bundle. The adapter also prefixes legacy `node --experimental-strip-types` invocations. Vendored prose receives the depth-independent retarget too. An mcp-only install writes `.codex/config.toml`, using `env_vars = ["NAME"]` to forward secrets rather than literal `${NAME}` values. **Project-local install** (`--dest` ≠ `$HOME`) warns with the `STARK_PLUGIN_ROOT` / `STARK_ASSET_ROOT` exports required by the `$HOME` fallback. **Not covered:** `--runtime claude` doesn't vendor because its committed `dist/claude/` plugin tree already does; no bundle targets the `gemini` runtime today (the gemini adapter exists, but no bundle ships a gemini artifact).

**Per-bundle plugin assets.** A bundle generated from a stark-skills `plugins/<bundle>/` plugin (`stark-gh`, now retired, was such a bundle; none is plugin-backed today) often has **plugin-specific** tools + its own `config.json` that the shared snapshot does NOT carry — the shared `tools/` is stark-skills' top-level dir, not `plugins/<bundle>/tools/`. `stark sync` captures these into `vendor/plugins/<bundle>/` (`importer.PluginVendorSnapshot`: `tools/**` `.ts` + `config.json` + `package.json`), and `stark build` layers them into that bundle's `dist/claude/<bundle>/` **after** the shared snapshot, so the plugin's own files win (e.g. stark-gh's `gh_*.ts` tools + its `{draft}` `config.json` override the global `config.json`). Without this, commands like `/stark-gh:cleanup` crash with `MODULE_NOT_FOUND` because their `${CLAUDE_PLUGIN_ROOT}/tools/gh_cleanup.ts` was never vendored.

## Layout

- `catalog/<bundle>/` — `bundle.yaml` + `mcp/` are **curated** (edit here); `skills/` + `commands/` are **generated** by `stark sync` from stark-skills (do not hand-edit). The generated two carry `linguist-generated=true` (STARK-7363): GitHub collapses them by default so a sync PR's curated changes stop being buried, and stark-skills' `findings_review_post.ts` reads this repo's rows **at the PR head** and reports findings on those paths in the review **body** rather than an inline thread — an inline one can't be resolved by fixing the file here (the fix is upstream), and `main` enforces `required_conversation_resolution`, so on the shared `auto/marketplace-sync` branch such a thread blocks the publish. Two things the rows do **not** do. (1) They don't switch that routing on: stark-skills' own config already extends the resolved list for this repo with `catalog/**` (`generated_paths.repos["21StarkCom/bifrost"].add`, STARK-6095), which layers on top of whatever this file says — so *every* catalog path, including the `bundle.yaml` and `mcp/**` left unmarked here on purpose, is demoted to the body until that entry is narrowed **there** — which is STARK-7536 (stark-skills#1029), sequenced to land after this repo declares its rows, since narrowing first would send the generated copies back to opening blocking threads. `agents/` is unmarked for the same reason `mcp/` is: `runSync` manages only `skills/` and `commands/`, so an `agents/` dir would be curated. (2) They don't weaken a CODEOWNERS gate, because there is none to weaken — `require_code_owner_reviews` is `false` and `required_approving_review_count` is `0` on `main` (measured again 2026-09-19; see `docs/SECURITY.md` §5). What actually holds these bodies is the mandatory `/code-review xhigh --fix` gate and `publish-sync-pr`'s operator attestation. The rows are pinned by `engine/cmd/stark/gitattributes_test.go` — nothing in bifrost CI reads `.gitattributes`, so without it a dropped or misspelled row changes routing in the *other* repo while every gate here stays green. And bifrost#264 is **not** evidence for these rows: its 42 threads were 40 under `vendor/stark-skills/tools/` plus 2 on `CHANGELOG.md` — `vendor/**` was already marked; what was missing that day was the routing tool itself, which landed hours later (STARK-5637).
- `catalog/standards/` — **generated** copy of stark-skills' `standards/`, emitted by `stark sync` and the one directory under `catalog/` that is NOT a bundle (STARK-6357). Skill bodies link `../../standards/*.md`; from `catalog/<bundle>/skills/<name>.md` that resolves here, so without it all 68 were dead when the catalog is browsed on GitHub — which is the only place it IS browsed. Making the target exist beats rewriting the links: a retarget rule would re-render every bundle's catalog bytes and force a version bump of all seven, where this changes no skill copy and no `dist/` byte. `load.ReservedCatalogDir` skips it **by name** — skipping any dir without a `bundle.yaml` would be fail-open, letting a real bundle with a missing or misnamed manifest vanish from every gate while they reported clean. The name is exempt from being *read* as a bundle, not from *colliding* with one: a `catalog/standards/bundle.yaml` is a hard `load.Load` error, because a bundle parked there would be invisible to every gate AND deleted by the next `sync` (it is a managed root). Pinned by `TestEveryCatalogStandardsLinkResolves` + `TestCatalogStandardsMatchesTheVendoredSnapshot` (both walk the real tree — the second is the only in-repo drift gate on this copy, since bifrost CI runs `build --check` but never `sync --check`) and the reserved-dir tests in `internal/load`.
- `vendor/stark-skills/` — **generated** normalized snapshot of stark-skills' immutable assets (tools/prompts/standards/scripts/config), refreshed by `stark sync`, vendored into **every** plugin by `stark build`. Committed, `linguist-generated`. **Version-gated since STARK-4986:** `stark build` records one `digest.Files` hash of this tree in `index.json`'s `sharedAssets` — once per bundle, because the version it must force a bump of is per bundle — and `check-bumps` holds it to the same immutability rule as artifacts. Without those rows a change confined to a top-level `tools/*.ts` touched no artifact digest and no `pluginAssets` digest, so the gate reported clean while all seven dist trees shipped changed bytes under unchanged versions; measured live 2026-09-16 on PR #244 (the `/team-leader-agent` → `/gru` rename), where a code review caught it and the gate did not.
- `vendor/plugins/<bundle>/` — **generated** per-bundle asset snapshot, refreshed by `stark sync` and layered by `stark build` into that bundle's dist tree (winning over `vendor/stark-skills/`). Holds a stark-skills `plugins/<bundle>/` plugin's own `tools/**` + `config.json`/`package.json` (no bundle is such a plugin today — `stark-gh` was the last, now retired) and/or member skills' `references/`/`scripts/`/`assets/` dirs (for any bundle whose skills carry them). A bundle appears here with either — currently **five**: `stark-analyze`, `stark-design`, `stark-implement`, `stark-ops`, `stark-plan` (none is genuinely plugin-backed since `stark-gh` was retired; all are here to carry skill assets). Committed, `linguist-generated`. **These assets are version-gated:** `stark build` records a `digest.Files` hash per bundle in `index.json`'s `pluginAssets`, and `check-bumps` holds it to the same immutability rule as artifacts. Without that row a change confined to a plugin's `tools/**` touched no artifact digest, so the gate reported clean and the bundle shipped modified content under an unchanged version that consumers would never re-fetch — hit live 2026-07-27, when a `stark-gh` `lib/git.ts` fix shipped un-bumped at 0.1.10.
- `vendor/runtime-overrides/codex/<bundle>/` — **source-owned** Codex-only overlay, layered by `stark build` into that bundle's `dist/codex-plugins/<bundle>/` package only (never `dist/claude/`). Six bundles carry one today. **Version-gated since STARK-4986**, on the same rule as the two trees above: `stark build` records a `digest.Files` hash per overlay bundle in `index.json`'s `codexAssets`, so an overlay edit cannot ship to Codex installs under an unchanged bundle version.
- `engine/` — Go CLI (`cmd/stark`) + libraries (`internal/{adapter,build,validate,importer,install,...}`). Per-runtime adapters live under `internal/adapter/{claude,codex,gemini}`. The generator lives in `cmd/stark/sync.go` + `internal/importer/{importer,vendor,serialize}.go`.
- `engine/internal/starktui/` — **generated** `cp -R` snapshot of stark-tui's `go/help` + `go/colors`, pinned at `go/v0.3.3`; `cmd/stark/help.go` renders every help page through it (STARK-6770, epic STARK-7636). Committed, `linguist-generated`, **never hand-edited** — the fix for anything in here lands upstream, which is exactly why the rows exist: an inline review thread on this tree has no in-repo resolution, and `main` enforces `required_conversation_resolution`. A copy rather than a `require` because **stark-tui is private and this is the org's only public repo**: `ci.yml` carries only `secrets.GITHUB_TOKEN`, scoped here, so a private-module fetch reddens the required `engine` context, and no public clone could build either. Both packages are stdlib-only, so the snapshot adds **zero** module deps and `engine/go.mod` is untouched — pinned, along with the ban on importing bifrost's own packages from inside it (which would make the documented `cp -R` refresh destructive), by `cmd/stark/starktui_snapshot_test.go`. Refresh recipe + the pinned upstream commit: `engine/internal/starktui/README.md`. **cobra is why the seam is a func, not a template:** cobra owns its help/usage templates and a template cannot look at a rendered line and decide what it is, so `installHelpRendering` sets `SetHelpFunc` + `SetUsageFunc` on the **root only** (both walk to the parent, so all 14 subcommands plus cobra's generated `help`/`completion` inherit). `plainHelp` mirrors cobra's unexported `defaultHelpFunc`; `plainUsage` clears the usage func **on the root** for the duration of `c.UsageString()`, because that call routes through `c.Usage()` and would otherwise recurse forever out of `stark help <unknown-topic>` and double-paint every help page. Help TEXT stays plain authored strings: off a terminal the page is byte-identical to cobra's, pinned command-by-command against a pristine tree in `cmd/stark/help_test.go` — which is also the only thing holding `plainHelp` to cobra's own composition across a cobra upgrade (it compares against the live `HelpFunc()`, because cobra's `defaultHelpFunc` and `defaultHelpTemplate` themselves disagree on a whitespace-only description and it is the FUNC that ships). **`helpOptions` asks for NO column budget** — not even on a terminal, which is deliberately *not* `help.For`'s default: the renderer folds any 4+-space-indented line into the item row above it, right for a hand-wrapped page and wrong for pflag's, which prints a shorthand-less flag at a 6-space indent while `  -h, --help` sits at two. With a budget, `stark install --help` on a real terminal collapsed eight flag rows into the `--help` row. Cobra and pflag already aligned this page; the fleet look is the palette, not a second layout pass. `TestHelpIsNeverColumnFitted` pins the decision and `TestColumnFittingWouldGarbleCobrasFlagBlock` is the tripwire that reddens once an upstream refresh fixes the rule and the budget can come back.
- `dist/claude/` and `dist/codex-plugins/` — **committed** native marketplace packages. `dist/codex/` and `dist/gemini/` are **not committed** standalone outputs, built on `stark install`.
- `bundles/*.json`, `index.json` — committed, signed registry payloads. Marked `linguist-generated`.
- `schema/` — JSON Schemas (`bundle`, `artifact.{skill,command,agent,prompt,mcp}`). Fail-closed in CI.
- `.claude-plugin/marketplace.json` — repo-root CC marketplace manifest (must stay at repo root; CC resolves plugin `source` paths relative to it).
- `docs/` — `native-install-loop.md`, `SECURITY.md`, `operations/branch-protection.md`, `operations/rollback.md`. Read these before changing install/deploy/governance behavior.

## Common commands

Engine (run from `engine/`):
- `go test ./... -count=1` — unit + golden + determinism + integration
- `go vet ./...`
- `go run ./cmd/stark sync --from <stark-skills> ../catalog` — **regenerate** catalog skills/commands + `vendor/` from the source repo (`--check` = drift gate)
- `go run ./cmd/stark validate ../catalog` — fail-closed schema + cross-ref
- `go run ./cmd/stark build --check ../catalog` — **drift gate**; rebuild must equal committed `dist/claude/` + registry (vendors `vendor/stark-skills` into each bundle)
- `go run ./cmd/stark check-bumps ../catalog` — version-bump immutability (bump the **bundle** version to publish a content change)
- `go run ./cmd/stark lint ../catalog` — body suspicious-pattern scan (advisory; CI runs `lint --strict`, which IS blocking)
- `go run ./cmd/stark install <bundle> --runtime claude|codex|gemini` — render into local config (codex also vendors `vendor/stark-skills` + `vendor/plugins/<bundle>`; `--assets-source` / `--plugin-assets` override, `--plan` previews)

Don't argue against enrolment from this file — `docs/operations/branch-protection.md` §1 carries the full comparison and is the one place to change it. What stays true either way: **do not add the context to the ruleset by hand here.** Every other repo's requirement is Terraform state in 21stark; a hand-made one is invisible to that tier's audit and gets orphaned by the next fleet pin bump that renames the context's right half, which blocks every merge on "Expected — waiting for status" until an operator edits the ruleset back out (bifrost's own `Required CI on main` does carry a repo-admin bypass actor — see §3 — but the fleet tier's rulesets deliberately carry none). Enrolment belongs in 21stark, not in `gh api ... /rulesets` from here. A context string is the job's `name:`, not its YAML key, so renaming a job orphans the requirement and the merge box waits forever; update the ruleset in the same change. So the bytes arrive by PR. Change the template in 21stark and copy the new render; never edit the body here. Pinned by `engine/cmd/stark/secret_scan_caller_test.go`. **The `google-oauth-client-secret` rule in `.gitleaks.toml` is load-bearing for it:** the reusable workflow's self-test asserts that exact rule id fires before it will trust a clean scan, so removing or renaming the rule turns the check RED on a repo with no secrets in it. It verifies `aryeh-stark`'s attestation on the *exact* current head (`<!-- stark-code-review:complete -->` alone on line 1, naming `/code-review xhigh --fix`; CRLF-normalized; latest submitted review wins), then un-drafts → asserts the **required** check runs exist → `gh pr checks --required --watch --fail-fast` → re-reads the head → asserts `compare` is `ahead` → re-reads the attestation → `gh pr merge --squash --match-head-commit` → dispatches `sign-manifest`. **`--required` is load-bearing, not cosmetic:** a `pull_request_review` run attaches its check run to the PR's HEAD commit exactly as a `pull_request` run does, so an unfiltered `--watch` waits on this very job and can never converge; the required set is the ruleset's three `ci` contexts, which is the gate `main` actually enforces — and which is also what keeps the unrequired `secret-scan / secret-scan` out of the watch list. **The trailing `sign-manifest` dispatch is load-bearing too:** the squash push is made with `GITHUB_TOKEN`, and GitHub's anti-loop guard starts no workflow run for it (the same guard `sign-manifest.yml` already names for tag pushes) — under the old design the merge came from stark-skills' App token, which did trigger it. `sign-manifest` therefore also accepts `workflow_dispatch`; it stays idempotent per-SHA. **That same guard silently costs `secret-scan` its push-to-`main` run**: the auto-published sync merge is the commonest way a commit reaches `main` here, and no `push` workflow starts for it — so `secret-scan / secret-scan` is absent from `commits/main/check-runs` on exactly those SHAs, and `secret-scan.yml` cannot be dispatched to cover the gap because the fleet render carries no `workflow_dispatch` trigger. Read the fleet sweep accordingly, and fix it in the 21stark template (adding a trigger HERE would break the byte-identity the drift check relies on). The job never checks out, so it sets `GH_REPO` (gh reads git remotes, never `GITHUB_REPOSITORY`), and it refuses a cross-repository head — `pull_request_review` fires for fork PRs and `headRefName` carries no owner. A review that is not an attestation exits **green having merged nothing**, so ordinary comments don't redden the PR — but green is reserved for an actual *verdict*. `completed_review` maps its check onto **three** outcomes, never two: `0` attested, `1` not attested, `2` could-not-tell. Only `1` is green; an unreadable reviews API **and a predicate that errors out** both take `2` and withhold publication with a red run. `jq -e` exits `1` for a false/null result but `2`/`3`/`4`/`5` for usage, compile, no-result and runtime errors, so returning its status raw made a broken predicate indistinguishable from "nobody attested" — publication stopped forever, every run green, no alarm anywhere, which is the exact silent stall STARK-6208 was filed to end. Membership is therefore read from each `bundle.yaml`'s `skills:` block rather than grepped as `- stark-` lines, so an unprefixed name can't collide with the `tags:`/`runtimes:` lists. Add a new skill to a bundle (or `--add-skill`), or exclude it deliberately. **It is its own script so BOTH paths can call it (STARK-6468).** While it lived inline in publish.sh it guarded only the MANUAL regen; the path that actually publishes is stark-skills' `marketplace-sync.yml`, which regenerates bifrost and opens the sync PR on ~every release and never invoked publish.sh. Its gate list (`validate`, `sync --check`, `build --check`, `check-bumps`) is entirely internal-consistency checks between bifrost's own catalog and dist — none of them looks back at the stark-skills tree to ask whether every skill is claimed — so the automated path had **no coverage gate at all**. That is how `agnes` shipped un-membered at v0.31.2 (STARK-6249) with every gate green while the same release published `standards/worker-spine.md` naming `/agnes`. **Three callers run it now** (STARK-6468 parts 1 + 2): `publish.sh` before its VERSION bump; stark-skills' `marketplace-sync.yml` before the regen, which is what actually closes the hole; and stark-skills' `tests.yml` on every `pull_request` (its `test` job, a **required** context there), so an unclaimed skill goes red on the PR that adds it. Read a RED `marketplace-sync` as "publication is stopped", not "unpublished but fine". **Both stark-skills callers execute `docs/scripts/coverage-gate.sh` out of a checkout of THIS repo's default branch** (`marketplace-sync` already has one; `tests.yml` clones bifrost to `.bifrost-gate`), which makes two things contracts rather than conveniences. One: only membership already **merged to `main` here** satisfies the PR-time gate — an open bifrost PR does not. Two: **never move, rename or drop the exec bit on `docs/scripts/coverage-gate.sh`** without editing both stark-skills workflows in the same window; each prints a named `::error::` rather than dying at 126/127, but both go red and publication stops. `engine/cmd/stark/coverage_gate_test.go` pins the path and the exec bit from this side. **Landing a new skill is ONE window, not two independent merges.** Land the bundle membership here first — generated by `stark sync --from` the *unmerged* stark-skills branch, since `importSkills` is fail-closed on a declared member with no source — then merge the upstream skill immediately after: while bifrost `main` claims a skill stark-skills `main` does not yet carry, `marketplace-sync`'s `stark sync` hard-errors on **every** push, which is the same publication halt from the other side. **And note bifrost CI never runs this gate**: `ci` has no stark-skills checkout, and `coverage_gate_test.go` exercises the script against a fixture, not the real tree. Dropping a skill from a `bundle.yaml` here therefore merges green *here* and reddens stark-skills' required `test` check plus every `marketplace-sync` run — the orphan is created in this repo and only ever detected in the other one. **Never reimplement the check in the workflow** — two copies of a gate is how it ends up enforced in one place and not the other, which is this same bug one level up; `EXCLUDED_SKILLS` lives with the gate for the same reason. Pinned by `engine/cmd/stark/coverage_gate_test.go`, which runs the real script (including the exact v0.31.2 orphan state) rather than a copy of its logic. Note `marketplace-sync.yml`'s push trigger is path-filtered to `skill/**`, `tools/**`, `global/**`, `scripts/**`, `standards/**`, `runtime-overrides/codex/**`, so a workflow-only edit does not fire it — prove changes with `gh workflow run marketplace-sync.yml --ref main`. **Release-notes gate (2026-09-19, STARK-6249):** publish.sh ends by refusing to report success unless `CHANGELOG.md` carries a `## [<VERSION>]` heading with notes under it. The VERSION bump it just made IS the release trigger — `sign-manifest` tags `v<VERSION>` and reads the release body out of that section, falling back to the bare string `Release <VERSION>.` when it is missing — so a forgotten section ships a silent, empty release rather than failing. It also fails if `bump` left VERSION unchanged (it only rewrites a bare `X.Y.Z` line, silently otherwise), which would otherwise publish content under an already-tagged version and cut no release at all. The gate reads the section with `sign-manifest.yml`'s own line-anchored awk, not a `grep -F` lookalike that a prose mention of the heading would satisfy. It runs LAST, after the regen is drift-clean, on purpose: add the section and commit — do NOT re-run publish.sh to clear it, the VERSION bump is not idempotent. To reverse: `gh workflow disable <name>`.

**Every `stark sync` run prints the source checkout and its HEAD first (STARK-7364)** — `source: <absolute path>` then `<sha> <date> <subject>`, plus `+ UNCOMMITTED CHANGES` when the source's working tree differs from that commit (sync copies the tree, never the commit, so on a dirty source the sha alone is wrong about the bytes being vendored). Read it before trusting a regen: sync copies from whatever tree it is pointed at, so a stale checkout silently REGRESSES the shared snapshot for every bundle, surfacing only as an unexplained `git status` or a drift failure naming files you never touched (hit twice on 2026-09-19). It is a statement, not a staleness check, on purpose: "behind origin/main" would fire on the skill-membership recipe above, which syncs from an *unmerged* branch by design. A source it cannot read says so — and names git's own reason — rather than printing nothing.

**GOTCHA — `sync` alone is not enough; always follow with `build --fix`.** Adding a skill to a bundle (or any stark-skills change) is a **two-step** regen: `stark sync` refreshes `catalog/` + `vendor/`, but the committed `dist/claude/` tree, `bundles/*.json`, `index.json`, and `.claude-plugin/marketplace.json` are only regenerated by `stark build`. Commit a `sync` without a `build` and the **non-bypassable `build --check` drift gate fails CI** (`dist/.../stark_*.ts (missing)`, `bundles/<bundle>.json (changed)`, `index.json (changed)`). Full flow when touching membership: edit `bundle.yaml` (bump its `version`) → `go run ./cmd/stark sync --from ../../stark-skills ../catalog` → `UPDATE_GOLDEN=1 go test ./internal/adapter/...` (if adapter bytes moved) → `go run ./cmd/stark build --fix ../catalog` → `go run ./cmd/stark build --check ../catalog` (expect `OK: no drift`) → commit **everything** (catalog + vendor + dist + golden). The auto-publish `marketplace-sync` PR from stark-skills does run both steps — this gotcha bites **manual** membership edits made directly here.

## Architecture — the bits that need multiple files to understand

**Source → adapter → output.** `internal/load` reads `catalog/`; `internal/adapter/{claude,codex,gemini}` each implement a `Target` that renders a `model.Bundle` into a runtime-specific file tree. `internal/build` drives a full render; `internal/install` consumes a per-runtime render to write into a user's CC/codex/gemini config. `cmd/stark` wires these together. The `catalogAdapter` in `engine/cmd/stark/` is the production `installplan.Adapter` — renders **one artifact at a time** in a single-artifact sub-bundle so a multi-MCP bundle doesn't collide on its shared runtime config (`.codex/config.toml`, `.mcp.json`, or `settings.json`).

**Bundle assets are outside the artifact plan.** `installplan.Compute` walks *artifacts*, driven by each `bundles/<name>.json`'s per-runtime `outputs`. The vendored snapshot belongs to no artifact, so it rides the optional **`installplan.AssetProvider`** interface: an adapter that implements `BundleAssets(bundle, runtime)` gets one extra `Step` per installed bundle, **prepended** (artifacts win on collision, same precedence as `build.Build`) and kept out of the artifact **ClosureRefs** (it names no artifact). It is NOT out of the consent *gate*, though: the snapshot ships executable `tools/*.ts` + `scripts/*.sh` the skills invoke, so a bundle with executable assets sets `Consent.Required` and lists them in `Consent.AssetExec` (§9.3) even with no mcp/agent. Assets vendor only for bundles that installed an **asset-consuming** artifact (`consumesAssets` — everything except mcp); an mcp-only install pulls in none. The prepended asset step is also **exempt from the unmanaged-collision preflight** (`.agents/stark/<bundle>/` is an installer-owned namespace of immutable vendored content, so a stale leftover is overwritten, not a whole-install abort). `assetPathFor` in `adapter_wire.go` is where a runtime opts in; only codex has a layout today.

**Generation pipeline (stark-skills → catalog → dist).** `stark sync` (`cmd/stark/sync.go`) reads a stark-skills checkout and, per each `bundle.yaml`'s `skills:`/`commands:` membership, writes `catalog/<bundle>/{skills,commands}` via `importer.ImportForGenerator` + `ArtifactFiles` (preserving the curated `bundle.yaml` + `mcp/`), refreshes the shared `vendor/stark-skills/` via `importer.VendorSnapshot`, and refreshes each bundle's `vendor/plugins/<bundle>/` via `importer.PluginVendorSnapshot`. Generated artifacts inherit their bundle's `version` + `runtimes`. `stark build` then vendors `vendor/stark-skills/` into each `dist/claude/<bundle>/` (`build.Options.AssetsSource`, defaulting to `<repo>/vendor/stark-skills`) and layers `vendor/plugins/<bundle>/` on top for the owning bundle (`build.Options.PluginAssetsRoot`, defaulting to `<repo>/vendor/plugins`). Two drift gates: `sync --check` (catalog/vendor vs a fresh generation — cross-repo) and `build --check` (dist vs catalog). CI wires stark-skills → here automatically (auto-publish PR on stark-skills `main`).

**Determinism is load-bearing.** `build --check` is the drift gate. Any change that re-renders bytes — adapter output, schema, canonicalization (`internal/canonjson`), aggregate index (`internal/aggregate`), digest (`internal/digest`) — will fail CI unless you also commit the regenerated `dist/claude/`, `index.json`, `bundles/*.json`. Workflow: edit catalog → `go run ./cmd/stark build ../catalog` → commit the diff.

**Distribution commit rule.** Commit generated `dist/claude/` and native `dist/codex-plugins/` marketplace packages. `dist/codex/` and `dist/gemini/` are standalone outputs produced by `stark install` on the user's machine; never commit them.

**Version-bump immutability** (`internal/bumps`): an artifact at a given version is content-locked. Bump the version when content changes; `check-bumps` blocks otherwise. Four row families feed it, all keyed `<bundle>/<kind>/<name>` so none can collide: artifact sources (`digest.Source`), per-bundle plugin assets (`pluginAssets`), the shared vendored snapshot (`sharedAssets`), and per-bundle source-owned Codex overlays (`codexAssets`, `vendor/runtime-overrides/codex/<bundle>` → `dist/codex-plugins/<bundle>`). **The rule that generates that list: every vendored tree `stark build` ships needs a row the day it starts shipping** — it carries no `digest.Source`, so without one the gate reports clean over content it never inspected. **That rule stops at vendored trees: bytes the ENGINE derives are deliberately exempt (STARK-7977), and there is no fifth family for `dist/codex-plugins/<bundle>/.codex-plugin/plugin.json`.** Measured on bifrost#294 and again 2026-09-20: changing the homepage fallback in `internal/marketplace/codex.go` re-renders six manifests, no bundle version moves, and `check-bumps` prints `OK` — by design, for two reasons. One: spec §11 has the gate hash canonical *source* and says display-metadata-only changes (`description`/`tags`/homepage/owner) do **not** force a bump; the manifest is almost entirely that metadata, so a row digesting its bytes would make every `bundle.yaml` description edit a violation. Two: the Codex manifest's `version` is the root `VERSION`, not the bundle's (stark-ops: `0.32.3` vs `0.17.3`), and the bundle version appears nowhere in the Codex package — so the only bump this gate can force reaches no consumer of the changed bytes. It is the same class as any other engine-driven re-render (an adapter edit re-renders every skill body under unchanged bundle versions), which spec §7.7 gives to the adapter target version, not to this gate. Both premises are pinned, so the exemption reddens rather than outliving them: `TestCheckBumpsExemptsACodexManifestOnlyChange` and `TestCommittedCodexManifestsCarryTheRootVersion`. The gap that reasoning exposes — nothing forces the root `VERSION` to move when `dist/codex-plugins/**` changes on a hand PR — is **STARK-7998**, and a row there would subsume the manifest; don't bolt a per-bundle manifest row on here in the meantime. That key prefix is also a machine contract — `docs/scripts/publish.sh` auto-bumps by sed-ing the bundle name off the front of each `  - <bundle>/…` violation line, so changing the line shape silently stops it bumping while `check-bumps` alone still looks correct (pinned by `TestPublishShParserExtractsBundlesFromSharedAssetViolations`, which runs the real script's real parser over real gate output).

**Registry signing.** `sign-manifest.yml` workflow signs `index.json`.

## Conventions

- **Go 1.24**, module `github.com/21StarkCom/bifrost/engine`. Standard layout (`cmd/`, `internal/`), small packages.
- **Never hand-edit `dist/`, `index.json`, or `bundles/*.json`.** Regenerate via `stark build`.
- **CODEOWNERS** names the owners of schema, adapters, governance and signing — respect those ownership lines; don't route around them. It is **not an enforced merge gate today**: `require_code_owner_reviews` is `false` and `required_approving_review_count` is `0` on `main` (measured 2026-09-19; `docs/SECURITY.md` §5 explains why on a single-operator repo, and `docs/SECURITY.md` §3's approval table states the policy, not the live setting). What actually holds these paths is the mandatory `/code-review xhigh --fix` gate plus `publish-sync-pr`'s operator attestation.
- See `docs/native-install-loop.md` for the CC install loop, `docs/SECURITY.md` for the threat model and signing policy, and `docs/operations/branch-protection.md` for what `main` gates on.
