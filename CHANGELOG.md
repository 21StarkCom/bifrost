# Changelog

All notable changes to `bifrost`. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [SemVer](https://semver.org/spec/v2.0.0.html). There is no repo-level version any more: `VERSION` and `sign-manifest.yml` are gone, nothing cuts a tag or a release, and the release chain ended at **v0.32.3** — so everything under `## [Unreleased]` stays unreleased. The versions that still move are the seven per-plugin `version` fields in `.claude-plugin/marketplace.json`, which is what a Claude Code install keys its re-fetch on.

## [Unreleased]

### Removed
- **bifrost stops being a marketplace operation (STARK-8249, phase 2 of STARK-8248).** The generate → build → sign → publish pipeline and everything that existed to feed it are deleted: `engine/` (the Go `stark` CLI, all three runtime adapters, and every gate it carried — `validate`, `build --check`, `check-bumps`, `lint --strict`, `allowlist --check`), `catalog/`, `dist/`, `vendor/`, `bundles/*.json`, `index.json`, `schema/`, `VERSION`, `.goreleaser.yaml`, `.gitattributes`, `.agents/plugins/marketplace.json`, `CONTRIBUTING.md`, the `sign-manifest`, `publish-sync-pr` and `sync-pr-watchdog` workflows, `docs/{SECURITY.md,native-install-loop.md,allowlist.md,specs/,retros/}`, `docs/operations/{rollback,positional-help-audit}.md`, `docs/scripts/*.sh`, `scripts/benchmarks/` and `skill/evals/`. Tracked files **2,705 → 327**. The pipeline had exactly one input — a stark-skills checkout — and that tree now lives here (see the STARK-8249 phase-1 entry under Added), so every root it generated was a second copy of files this repo already owns. `docs/scripts/coverage-gate.sh` goes with it, which is why stark-skills' own coupling had to be cut **first** (stark-skills#1035): its required `test` job checked this repo out and `exit 1`d when the script was absent, so landing this side first would have reddened every PR in that repo with no green path to fix it. **One compensating gain, worth stating because nothing else will:** with `sign-manifest`, `publish-sync-pr` and `sync-pr-watchdog` gone, no workflow here holds any write permission — `ci.yml` and `secret-scan.yml` are both `contents: read`, and those two are now the whole of `.github/workflows/`.
- **Signing, `v<VERSION>` tags and GitHub Releases end at v0.32.3 — this bullet is the only record that they did.** `sign-manifest.yml` was the sole producer of all three: the cosign-keyless signature over `build-manifest.json` (GitHub OIDC → Fulcio → Rekor, self-verified in-run by `stark verify-manifest`), the `v<VERSION>` tag cut whenever `VERSION` moved, and the GitHub Release whose body it extracted from this file's `## [<VERSION>]` section. It had no required context and fired on `push: main`, so **its deletion is silent by construction**: `main` just stops producing signed manifests, tags and releases, with every gate green and nothing anywhere reporting the change. Existing tags and releases through **v0.32.3** (2026-09-19, the last one) are untouched, immutable and still verifiable — a consumer pinned to one keeps working and would never learn the chain stopped. Nothing new will be tagged: there is no `VERSION` file to bump and no manifest to sign, so every entry under `## [Unreleased]` from here on stays unreleased, permanently.
- **Native Codex install is retired.** `stark install --runtime codex` rendered `.agents/skills/<name>/SKILL.md`, `agents/openai.yaml` and the per-bundle assets root under `.agents/stark/<bundle>/`; `dist/codex-plugins/` plus `.agents/plugins/marketplace.json` were the committed native Codex marketplace package and the manifest that pointed at it. The renderer lived in `engine/`, so all of it goes with the pipeline. `runtime-overrides/codex/` **stays** — 54 files of Codex-specific skill and standards text, after dropping the two overlays that were byte-identical to the shared copy and so overrode nothing (`standards/{stand-down,worker-spine}.md`, verified by hash) — but it is now source with nothing behind it: no command in this repo turns it into an installable Codex tree, and no `codexAssets` row gates it because `index.json` is gone. Claude Code is the only runtime this repo installs into today.
- **The web registry is gone (STARK-7972).** Deleted the `web/` React SPA, the `server/` Go static origin, the `Dockerfile`, the `web-deploy` workflow, `docs/scripts/deploy-web.sh` and `docs/web-hosting.md`. Nothing in the install or publish path read `marketplace.21stark.com`: Claude Code installs from `.claude-plugin/marketplace.json` + `dist/claude/` on GitHub, `stark install/search/info` load `index.json` from disk, and `sign-manifest` signs the committed `index.json` regardless of hosting. `index.json` / `bundles/*.json` stay. `ci.yml` drops the `web build` and `server (static origin)` jobs, so the required contexts on `main` go **five → three**; **this is a merge blocker, not a same-PR step** — narrowing the ruleset is an operator-only `gh api .../rulesets` mutation (`docs/operations/branch-protection.md`; SECURITY.md §5 forbids running it from an agent, skill, hook, or CI), so it must land *before* this change merges or every subsequent PR to `main` sits blocked waiting on two checks that no longer report (tracked live on STARK-7972). `publish.sh` loses `--deploy`. Codex plugin `homepage` / `websiteURL` now fall back to the GitHub repo URL. The GCP teardown in `ev-infra-group` is tracked separately.

- **`sync-pr-watchdog` — the first thing that reports a stranded `auto/marketplace-sync` PR (STARK-8164).** `publish-sync-pr` refuses to merge unless `compare(main...head).status` is `ahead`, and it runs **only** on `pull_request_review: [submitted]`. Those two facts do not compose: the precondition is falsified by a *different* event — any merge to `main` leaves the sync branch `diverged` — and that event starts no publication attempt, so nothing evaluates the precondition and nothing reports it. **An event-triggered workflow cannot observe the absence of its own event**, which is why no amount of hardening inside `publish-sync-pr` would ever have caught this. Measured live 2026-09-20: PR #293 opened 03:52, six hand merges landed on `main` between 08:10 and 13:30 (`sign-manifest` ran on each, so operator merges *do* fire push workflows), and the strand was found by hand at ~15:24 — **11.5 hours, six causing events, zero runs, zero alarms**, with publication of *every* stark-skills change stopped for the window, not just #293's. The new workflow asks one question — can `publish-sync-pr` still succeed on the open sync PR — on `push: main` (which names the causing merge at the instant it happens), on a half-hourly cron (which covers a merge made with `GITHUB_TOKEN`, for which GitHub starts no push run, plus an attestation spent on a publish run that then failed), and on `workflow_dispatch`. A non-ok verdict upserts **one** comment on the sync PR naming the remediation and fails the run (and re-posts nothing while the body is unchanged, so a half-hourly cron does not rewrite it 48 times a day). Two details are load-bearing in the query rather than in the verdict: the backstop clock runs from the **head commit**, not from `createdAt` — the sync branch is long-lived and force-pushed, so one reused PR carries regeneration after regeneration and #293's creation time was already 11.5 hours behind its head — and the PR it watches is filtered on `isCrossRepository`, the same guard `publish-sync-pr` carries, because `--head` matches a ref name that carries no owner and `gh pr list` answers newest-first. It deliberately does **not** restate `publish-sync-pr`'s attestation predicate (two copies of a gate is how one drifts, and every other publication failure already produces a red run of its own), and it deliberately does **not** repair: repair is a *regeneration*, needing a stark-skills checkout and a token for that repo which bifrost does not have, and a rebase instead would silently revert whatever `main` changed under `catalog/`/`dist/` — exactly the damage the refusal exists to prevent. The verdict jq is **extracted from the shipped workflow** and driven through real jq by `engine/cmd/stark/sync_pr_watchdog_test.go` (the `publish_sync_pr_test.go` idiom), covering `ahead`/`behind`/`diverged`/`identical` and the age boundary; the trigger and red-exit pins are asserted structurally after both were mutation-tested and the first drafts of each were found to pass a broken workflow.

- **Open-time ticket field stamp: `copilot_land land` and `/stark-author` Phase 6 write `pr_url` + `pr_state=open` (STARK-6108** — alfred spec STARK-6093 node T7). Alfred owns the ClickUp field schema; the path that opens a PR is the one authority for those two fields, and the whole interface is `alfred task edit --field` — nothing here touches ClickUp. New `tools/ticket_fields_lib.ts` carries the spec's resolution ladder, identical in every repo: explicit `--ticket` → the branch's `STARK-n` → alfred's bound ticket (`repo info --json`) → none. Two rules shape it. **A field write never fails the PR verb:** nothing throws, and a missing `alfred`, an unparseable `repo info`, a Jira handle, an unset `clickup.space_id` or the `pr_state` ladder refusing a backwards move all degrade to a skip — turning "the ticket lacks a URL" into "the PR was never opened" is strictly worse. **A skip is visible:** every outcome renders exactly ONE `ticket fields: …` line (the wording idun's half is *specified* to print, so one grep will find both repos' skips once its T6 lands — verified absent from idun `414c0f7`, where STARK-6107 was still in flight), because a silent skip is indistinguishable from a successful write, which is how a whole plane of ticket state stays empty. **An alfred exit 0 that wrote nothing counts as a skip:** with `clickup.space_id` unset, `alfred task edit --field` prints `fields: skipped (…)` and exits 0 (the spec: nothing about fields makes a config red), so `alfredSkipReason` reads it off the answer and the line says *skipped* rather than claiming a write over an untouched ticket — an empty `fields_set` is deliberately NOT read that way, since a same-value re-write journals nothing and `land` re-runs on the adopt path by design. `land` stamps on the **adopt** path as well as create — the PR is open either way, a same-value write journals nothing, and a re-run is then the only repair available for a first run whose write failed, since the second run always adopts. For those the heading was simply false, and the contradiction was visible in one screen — the generated-path preamble promises "each is listed below with the file and line it would have anchored to", and the heading directly beneath it said they were out of diff. A reader seeing a CONFIRMED finding on `vendor/stark-skills/tools/gru.ts:11` under "out-of-diff findings" reasonably concludes it was outside the PR's scope, which is exactly the "downgraded away" outcome that preamble promises never happens. **The caller states the reason; the renderer never infers it** — by the time a finding reaches `buildReviewBody`, a withheld in-diff finding and a genuinely out-of-diff one are indistinguishable from file/line alone. New optional `Finding.body_reason` (`finding_lib.ts`, today the single value `generated_path`); `planReview` sets it on every demoted finding; `buildReviewBody` groups on it and emits one heading per group — `OUT_OF_DIFF_HEADING` for the unlabelled group, `BODY_REASON_HEADINGS.generated_path` = "## Findings on generated paths — withheld from inline threads" for the other. **The generated heading asserts neither in-diff nor out-of-diff, deliberately.** Saying "in-diff" would be the same falsehood pointing the other way: a reviewer can report a finding on a generated file the PR never touched, which is genuinely both, and its entry's own note already reads "outside this PR's diff" — a heading contradicting the line under it is exactly what this ticket set out to remove. `generatedFindingNote` is the only place that knows which case an entry is, so it is the only place that says. **Presentation only:** routing, severity, `classification`, disposition and inline rendering are untouched, and no finding moves between the body and a thread. **Labelled groups render first**, because the generated-path preamble lives in `humanSummary` above every group and promises "each is listed below" — with the unlabelled group first, that sentence pointed at the out-of-diff findings instead of the ones it introduces. The list is now resolved per run with a stated, per-layer-tested precedence — `--generated-paths` > `generated_paths.repos["O/R"].paths` > the target repo's own `.gitattributes` rows (fetched via `gh api repos/O/R/contents/.gitattributes`, so the repo need not be checked out) > `generated_paths.default` — plus, on top of whichever layer won, that repo's config `add` list and then the new **`--add-generated-paths`**, because extending used to mean restating every other glob and forgetting one re-enabled gating threads on that path. Deliberately **not** a gitattributes parser — it takes `linguist-generated` Set (`=true` or bare, which in git IS Set) and skips `-`/`!`/`=false` rows and `[attr]` macros rather than guessing at last-match-wins precedence with negation; and a slash-less declared pattern stays **root-anchored** instead of git's basename-at-any-depth, keeping STARK-5637's deliberate choice that bifrost's declared `index.json` must not swallow its hand-written `web/src/__fixtures__/index.json`. **Fail-open, never fail-narrow:** an absent, unfetchable or generated-row-free `.gitattributes` falls back to the configured default, warns on stderr, and can never yield an empty list, because an empty list is a silent disable of the split — the exact failure the split exists to prevent; disabling stays explicit (`--no-generated-split`, `generated_paths.enabled: false`). `--add-generated-paths` is held to the same empty-value and flag-shaped-value refusals as `--generated-paths`. The resolved layer is disclosed in the JSON summary as `generatedPathSplit.source`, with `added` and `warnings`. Two hardening rules the review added: `generated_paths.enabled: false` is a GLOBAL default, so an explicit `--generated-paths` outranks it (only `--no-generated-split` disables a run the operator gave globs to), and a non-array glob list in config (`"default": "vendor/**"`) is refused rather than spread into the one-character globs `["v","e","n",...]`, which match nothing — a silent disable wearing a config typo's hat.
